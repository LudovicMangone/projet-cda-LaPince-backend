## 📚 Comprendre le modèle de branches

Avant de toucher à quoi que ce soit, il faut que tout le monde visualise la même chose.

```
main          ←── production, toujours propre, on n'y touche jamais directement
  └── dev     ←── pré-production, branche tampon, toujours fonctionnelle
        ├── feat/dashboard
        ├── feat/auth
        ├── feat/depenses-crud
        └── feat/alertes-seuils
```

### La règle absolue

| Branche | Rôle | Qui peut pusher directement ? |
|---|---|---|
| `main` | Code en production | ❌ Personne — PR obligatoire |
| `dev` | Intégration commune | ❌ Personne — PR obligatoire |
| `feat/xxx` | Ta fonctionnalité | ✅ Toi uniquement |

## 🧹 Biome — Linter et Formatter

### Pourquoi Biome

Biome remplace ESLint + Prettier en un seul outil, plus rapide et sans conflits de configuration. Il lint et formate en même temps, avec une config unique par repo.

### Installation

```bash
npm install --save-dev @biomejs/biome
npx biome init
```

### Configuration — `biome.json`

```json
{
	"$schema": "https://biomejs.dev/schemas/2.4.15/schema.json",
	"css": {
		"parser": {
			"tailwindDirectives": true
		}
	},
	"vcs": {
		"enabled": false,
		"clientKind": "git",
		"useIgnoreFile": false
	},
	"files": {
		"ignoreUnknown": false,
		"includes": ["**", "!node_modules", "!.next", "!dist", "!docs"]
	},
	"formatter": {
		"enabled": true,
		"indentStyle": "tab"
	},
	"linter": {
		"enabled": true,
		"rules": {
			"recommended": true
		}
	},
	"javascript": {
		"formatter": {
			"quoteStyle": "double"
		}
	},
	"assist": {
		"enabled": true,
		"actions": {
			"source": {
				"organizeImports": "on"
			}
		}
	}
}
```

### Scripts `package.json`

```json
"scripts": {
  "lint": "biome lint ./src",
  "lint:fix": "biome lint --write ./src",
  "format": "biome format --write ./src",
  "check": "biome check --write ./src"
}
```

### Exécution automatique à la sauvegarde — VSCode

Créer `.vscode/settings.json` à la racine de chaque repo :

```json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "biomejs.biome",
  "editor.codeActionsOnSave": {
    "quickfix.biome": "explicit",
    "source.organizeImports.biome": "explicit"
  }
}
```

> Chaque membre de l'équipe doit installer l'extension **Biome** dans VSCode (`biomejs.biome`).
> Sans elle, le format à la sauvegarde ne s'active pas.

### Exécution automatique via Husky (pre-commit)

```bash
npm install --save-dev husky
npx husky init
```

Contenu de `.husky/pre-commit` :

```bash
#!/bin/sh
npx biome check --write ./src
```

> Biome vérifie et corrige automatiquement le code avant chaque commit.
> Si des erreurs non corrigeables sont détectées, le commit est bloqué.

## ✍️ Convention de nommage des commits — Conventional Commits

### Types de commits

| Type       | Usage                                            |
| ---------- | ------------------------------------------------ |
| `feat`     | Nouvelle fonctionnalité                          |
| `fix`      | Correction de bug                                |
| `chore`    | Tâche technique (config, dépendances, Docker...) |
| `docs`     | Documentation uniquement                         |
| `test`     | Ajout ou modification de tests                   |
| `refactor` | Réécriture sans changement de comportement       |
| `style`    | Formatage, espaces (sans impact logique)         |

### Exemples

```
feat: ajoute formulaire d'ajout de dépense
fix: corrige calcul du total mensuel par catégorie
chore: configure docker-compose avec postgres
docs: ajoute instructions d'installation dans README
test: ajoute tests unitaires sur le service des alertes
refactor: extrait la logique métier dans depense.service.ts
```

### Convention de nommage des branches

```
feat/nom-de-la-feature       → nouvelle fonctionnalité
fix/description-du-bug       → correction de bug
chore/description            → tâche technique (config, docker, etc.)
docs/description             → documentation uniquement
```

**Exemples concrets pour La Pince :**

```
feat/auth-inscription-connexion
feat/dashboard-graphiques
feat/operations-crud
feat/budgets-categories
feat/alertes-seuils
feat/participants-gestion
feat/reimbursements-algorithm
fix/calcul-balance-projet
chore/setup-docker
chore/setup-prisma
chore/setup-biome
docs/readme-installation
```

**Règle d'or :** un commit = une chose précise. Pas de `"feat: plein de trucs"`.

## 📅 Workflow quotidien

### Début de session

```bash
# 1. Toujours commencer par mettre à jour dev
git switch dev
git pull origin dev

# 2. Créer ta branche de fonctionnalité depuis dev
git switch -c feat/nom-de-ta-feature

# 3. Travailler, coder, sauvegarder...
```

### Pendant la session — commiter régulièrement

```bash
# Vérifier ce qui a changé
git status

# Ajouter les fichiers modifiés (préférer fichier par fichier)
git add src/controllers/operation.controller.ts

# Ou tout ajouter si tu es sûr·e de ce que tu commites
git add .

# Commiter avec un message clair
git commit -m "feat: ajoute route POST /operations avec validation"
```

### Fin de session

```bash
# Pousser ta branche sur GitHub — même si ce n'est pas fini
git push origin feat/nom-de-ta-feature

# Si c'est la première fois que tu pousses cette branche
git push --set-upstream origin feat/nom-de-ta-feature
```

> Toujours pusher en fin de session, même si la feature n'est pas terminée.
> Ça évite de perdre du travail et ça permet à l'équipe de voir où tu en es.

### Créer la Pull Request

1. Va sur GitHub → "Compare & pull request"
2. **base = dev** (toujours, jamais main)
3. Titre clair, description de ce que tu as fait et pourquoi
4. Assigne un·e reviewer parmi tes coéquipiers
5. Attends l'approbation avant de merger


### 🔄 Après le merge d'une PR — que faire ensuite ?

Une fois ta PR approuvée et mergée dans `dev` :

```bash
# 1. Revenir sur dev
git switch dev

# 2. Récupérer les dernières modifications (dont ton merge)
git pull origin dev

# 3. Supprimer ta branche feature en local — elle ne sert plus
git branch -d feat/ta-feature-mergee

# 4. Créer ta nouvelle branche depuis dev à jour
git switch -c feat/prochaine-feature
```

> GitHub propose de supprimer la branche distante automatiquement après le merge
> via le bouton **"Delete branch"** sur la page de la PR — clique dessus aussi.
> La commande `-d` ci-dessus ne supprime que ta branche **locale**.

> Si Git refuse le `-d` en disant que la branche n'est pas fully merged,
> utilise `-D` (force) — ça arrive quand le merge a été fait via squash ou rebase sur GitHub.
