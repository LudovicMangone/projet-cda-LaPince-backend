### 🧱 ErrorHandler et Classes d'erreurs personnalisées — explication

---

#### Le contexte : pourquoi faire ça ?

Par défaut, quand une erreur se produit en JavaScript, on lance un objet `Error` générique :

```ts
throw new Error("quelque chose s'est mal passé");
```

Le problème : cet objet ne contient pas de code HTTP (`400`, `401`, `404`...).
Pour une API REST, on a besoin d'erreurs qui portent à la fois un **message**
et un **statut HTTP**. C'est ce que font les classes dans la libraire `lib/errors.ts`.

---

#### La classe mère — `HttpError`

```ts
export class HttpError extends Error {
  status: number;
  name;

  constructor(message: string, { status }: { status: number }) {
    super(message);
    this.name = this.constructor.name;
    this.status = status;
  }
}
```

`extends Error` — `HttpError` **hérite** de la classe native `Error`.
Elle récupère automatiquement tout ce qu'`Error` sait déjà faire (stack trace, message...).

`super(message)` — appelle le constructeur de la classe parente `Error`
avec le message. Obligatoire quand on utilise `extends`, et toujours en premier.

`this.status = status` — ajoute une propriété `status` qui n'existe pas dans
`Error` de base. C'est le code HTTP qu'on veut transporter avec l'erreur.

`this.name = this.constructor.name` — petit bonus : au lieu d'afficher
`"Error"` dans les logs, ça affiche le nom réel de la classe instanciée
(`"BadRequestError"`, `"UnauthorizedError"`...). Utile pour déboguer.

**Déstructuration dans les paramètres :**
```ts
{ status }: { status: number }
// ↑ on extrait directement `status` depuis un objet passé en argument
// ↑ le `: { status: number }` c'est l'annotation TypeScript qui dit
//   "cet objet doit avoir une propriété status de type number"
```

---

#### Les classes filles — `BadRequestError` et `UnauthorizedError`

```ts
export class BadRequestError extends HttpError {
  constructor(message: string) {
    super(message, { status: 400 });
  }
}
```

Ces classes **héritent de `HttpError`** et pré-remplissent le `status`
automatiquement. Plus besoin de se souvenir du code HTTP à chaque fois.

`super(message, { status: 400 })` — appelle le constructeur de
`HttpError` avec le bon code HTTP figé. L'appelant n'a plus
qu'à passer le message personnalisé.

---

#### La chaîne d'héritage complète

Error                        ← classe native JavaScript
└── HttpError        ← ajoute status + name
├── BadRequestError  ← status figé à 400
└── UnauthorizedError ← status figé à 401


---

#### Comment ça s'utilise concrètement dans l'API

```ts
// Dans un controller ou un service :
if (!user) {
  throw new UnauthorizedError("Token invalide ou expiré");
}

if (!body.name) {
  throw new BadRequestError("Le champ name est obligatoire");
}
```

---

#### Ce que ça apporte

| Sans classes custom | Avec classes custom |
|---|---|
| `throw new Error("non autorisé")` | `throw new UnauthorizedError("Token expiré")` |
| Pas de code HTTP sur l'erreur | `err.status` disponible partout |
| Gestion d'erreur complexe dans chaque route | Un seul middleware centralisé |
| Logs peu lisibles | `err.name` = `"UnauthorizedError"` dans les logs |




### 🛡️ Middleware global de gestion des erreurs — explication

---

#### Vue d'ensemble

Ce fichier exporte une fonction `errorHandler` qui est le **filet de
sécurité central** de toute l'API. Toutes les erreurs de l'application
atterrissent ici, sont identifiées, et reçoivent une réponse HTTP adaptée.

---

#### La signature de la fonction

```ts
export function errorHandler(
  error: Error,
  req: Request,
  res: Response,
  next: NextFunction,
)
```

Les 4 paramètres sont **obligatoires** pour qu'Express reconnaisse cette
fonction comme un middleware d'erreur. Même si `next` n'est jamais utilisé
ici, sa présence est indispensable — sans lui Express traiterait la fonction
comme un middleware normal et ne l'appellerait jamais en cas d'erreur.


---

#### Comment ce middleware est déclenché


```ts
// Express 5 — le throw avec l'appel d'erreur souhaité
throw new NotFoundError("Projet introuvable");
```


---

#### Les 3 cas gérés dans l'ordre

---

#### Cas 1 — Erreur de validation Zod → HTTP 400

```ts
if (error instanceof z.ZodError) {
  console.info("ZodError", error);
  return res.status(422).json({
    status: 422,
    error: z.prettifyError(error),
  });
}
```

Zod est utilisé pour valider les données entrantes (body, params, query).
Quand une validation échoue, Zod lance automatiquement une `ZodError`.

`z.prettifyError(error)` transforme l'erreur technique Zod en message
lisible par le front :

```json
{
  "status": 422,
  "error": "name: Required\namount: Expected number, received string"
}
```

---

#### Cas 2 — Erreur client contrôlée → statut HTTP de la classe

```ts
if (error instanceof HttpClientError) {
  console.info("HttpClientError", error);
  return res.status(error.status).json({
    status: error.status,
    error: error.message,
  });
}
```

Ce bloc attrape toutes les erreurs que **nous, nous lancons volontairement**
dans les controllers et services — `NotFoundError`, `ConflictError`,
`UnprocessableEntityError`, etc.

Comme elles héritent toutes de `HttpError`, un seul `instanceof`
suffit pour toutes les couvrir.

`error.status` et `error.message` sont les propriétés définies
dans les classes custom — le middleware n'a rien à deviner.

```ts
// Dans un service, tu lances :
throw new NotFoundError("Projet introuvable");

// Le middleware retourne :
// HTTP 404 { status: 404, error: "Projet introuvable" }
```

---

#### Cas 3 — Erreur serveur inattendue → HTTP 500

```ts
console.error("Internal server error", error);

res.status(500).json({
  status: 500,
  error: "Internal server error",
});
```

Si l'erreur n'est ni un `ZodError` ni une `HttpError`, c'est une
erreur **non prévue** — bug de code, base de données qui ne répond pas,
variable undefined, etc.

⚠️ Important 
Message générique `"Internal server error"` — on ne renvoie jamais le
détail de l'erreur réelle au client. Exposer un message comme
`"Cannot read property 'id' of undefined"` ou une stack trace donne des
informations précieuses à un attaquant.

---

#### Le flux complet résumé

```
throw new NotFoundError("Projet introuvable")
  │
  ▼
errorHandler
  │
  ├── instanceof ZodError ?        → 400 + message Zod formaté
  ├── instanceof HttpClientError ? → err.status + err.message
  └── autre                        → console.error + 500 générique
```
