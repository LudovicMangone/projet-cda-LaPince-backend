## 🧱 ErrorHandler et Classes d'erreurs personnalisées — explication

---

### Le contexte : pourquoi faire ça ?

Par défaut, quand une erreur se produit en JavaScript, on lance un objet `Error` générique :

```ts
throw new Error("quelque chose s'est mal passé");
```

Le problème : cet objet ne contient pas de code HTTP (`400`, `401`, `404`...).
Pour une API REST, on a besoin d'erreurs qui portent à la fois un **message**
et un **statut HTTP**. C'est ce que font les classes dans la libraire `lib/errors.ts`.

---

### La classe mère — `HttpError`

```ts
export class HttpError extends Error {
  status: number;
  name;

  constructor(message: string, { status }: { status: number }) {
    super(message);
    this.name = this.constructor.name;
    this.status = status;
  }
}
```

`extends Error` — `HttpError` **hérite** de la classe native `Error`.
Elle récupère automatiquement tout ce qu'`Error` sait déjà faire (stack trace, message...).

`super(message)` — appelle le constructeur de la classe parente `Error`
avec le message. Obligatoire quand on utilise `extends`, et toujours en premier.

`this.status = status` — ajoute une propriété `status` qui n'existe pas dans
`Error` de base. C'est le code HTTP qu'on veut transporter avec l'erreur.

`this.name = this.constructor.name` — petit bonus : au lieu d'afficher
`"Error"` dans les logs, ça affiche le nom réel de la classe instanciée
(`"BadRequestError"`, `"UnauthorizedError"`...). Utile pour déboguer.

**Déstructuration dans les paramètres :**
```ts
{ status }: { status: number }
// ↑ on extrait directement `status` depuis un objet passé en argument
// ↑ le `: { status: number }` c'est l'annotation TypeScript qui dit
//   "cet objet doit avoir une propriété status de type number"
```

---

### Les classes filles — `BadRequestError` et `UnauthorizedError`

```ts
export class BadRequestError extends HttpError {
  constructor(message: string) {
    super(message, { status: 400 });
  }
}
```

Ces classes **héritent de `HttpError`** et pré-remplissent le `status`
automatiquement. Plus besoin de se souvenir du code HTTP à chaque fois.

`super(message, { status: 400 })` — appelle le constructeur de
`HttpError` avec le bon code HTTP figé. L'appelant n'a plus
qu'à passer le message personnalisé.

---

### La chaîne d'héritage complète

Error                        ← classe native JavaScript
└── HttpError        ← ajoute status + name
├── BadRequestError  ← status figé à 400
└── UnauthorizedError ← status figé à 401

### La chaîne d'héritage complète

```
Error                        ← classe native JavaScript
  └── HttpError             ← ajoute code de status + name personnalisé
        ├── BadRequestError  ← status figé à 400
        └── UnauthorizedError ← status figé à 401
```

---

### Comment ça s'utilise concrètement dans l'API

```ts
// Dans un controller ou un service :
if (!user) {
  throw new UnauthorizedError("Token invalide ou expiré");
}

if (!body.name) {
  throw new BadRequestError("Le champ name est obligatoire");
}
```

---

### Ce que ça apporte

| Sans classes custom | Avec classes custom |
|---|---|
| `throw new Error("non autorisé")` | `throw new UnauthorizedError("Token expiré")` |
| Pas de code HTTP sur l'erreur | `err.status` disponible partout |
| Gestion d'erreur complexe dans chaque route | Un seul middleware centralisé |
| Logs peu lisibles | `err.name` = `"UnauthorizedError"` dans les logs |
